# Application registry

The registry is the single source of truth about Autoline's screens. Page objects in `Polaris.Autoline/Generated/` are produced from it; nothing about an Autoline screen is written in C# unless it is a quirk that JSON cannot express.

```
registry/
  autoline/
    <screen-id>/
      screen.json                 curated tier — reviewed like code
      observed.<version>.json     observed tier — generated by `probe snapshot`, never hand-edited
    interrupts.json               known unexpected windows and their policies
  schema/
    observed.schema.json
    screen.schema.json
    interrupts.schema.json
```

## Two tiers

**Observed** = what the probe saw. Facts about HWNDs. Overwritten on every capture. Versioned by Autoline version so you can `diff` across upgrades.

**Curated** = what the screen *means*: semantic names, locators, actions, what actions cause. Authored by a person or a model, reviewed, validated against the observed tier.

The validator refuses a curated entry whose locators don't each resolve to exactly one node in the screen's current observed snapshot. That's the mechanism that keeps the two tiers honest.

## Effects and outcomes

The valuable part of the curated tier is not the control list — it's `actions`. Every action states what happens next, as a condition the driver can wait on:

- `effects` — same-screen consequences: "Make and Model become non-empty", "Save becomes enabled".
- `outcomes` — a set of possible results, usually new windows: Save might land on the list screen, show a confirm, or show a validation error. The generated method returns which one occurred. Mark an outcome `isFailure: true` to have the generated method throw instead.

This is how bots stop sleeping: the page object knows what to wait for.

## Workflow

1. `probe snapshot --window "^Vehicle Stock - Edit"` at work → `observed.<version>.json`.
2. Write or generate `screen.json` (Claude Code can draft it from the observed file + a screenshot; a human checks names and actions).
3. `polaris-registry validate` — fixes until green.
4. `polaris-registry generate` — regenerates `Generated/`.
5. Write a contract test per action (work only) and run it.
6. Commit all of it in one PR.

Full steps in `docs/runbooks/add-a-screen.md`.

## Files in this folder

- `observed.example.json` — shape of a probe capture (values invented; replace with real captures).
- `screen.example.json` — a complete curated entry for an edit screen.
- `interrupts.example.json` — interrupt registry.
- `SCHEMA.md` — field-by-field reference for both tiers.
